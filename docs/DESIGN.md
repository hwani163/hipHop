# 라임노트 현대화 설계문서

> 작성일: 2026-09-14
> 상태: 설계 확정, 구현 전

---

## 1. 프로젝트 목표

한국어 라임 자체를 **정교하게 분석·검증·학습하는 도구**.

최신 트렌드(2016년 이후 트랩/멈블랩 등 플로우·사운드 중심)를 따라가지 않고,
**라임의 정확성과 밀도를 측정하는 것**을 본질로 삼는다.
그 위에 라임 검색과 가사 생성 기능을 얹는다.

---

## 2. 기존 시스템의 한계

기존 구현(`server/routes/*.js`, `public/scripts/modules/toKoreanChars.js`)은 사실상 재사용 불가.

| 항목 | 문제 |
|---|---|
| 매칭 방식 | 단어 전체의 모음 시퀀스 **완전일치**만 지원 → 길이가 다르면 매칭 불가 |
| 문장 단위 | 미지원. 문장을 넣으면 앞부분 모음까지 전부 일치해야 해서 거의 안 걸림 |
| 끝라임/내적라임 | 구분 불가 |
| 종성(받침) | 아예 무시 (중성만 추출) |
| 발음 | 표기 기준. 연음화·비음화 등 음운변화 미반영 |
| 보안 | DB 접속정보가 4개 파일에 하드코딩된 채 퍼블릭 저장소에 노출 |

## 3. 조사 결과 (설계 근거)

### 3.1 한국어 라임의 언어학적 기준

- 음절 구조 초성-중성-종성 중 **중성(모음) + 종성(받침)** 이 라임을 구성
- **모음이 공명도가 가장 높아** 라임의 기준이 됨
- 한국어는 강세가 없어 영어식 강세 기반 라임이 성립하지 않음 → 음절 배열·모음 특성·받침 구조가 라임을 결정

### 3.2 한국힙합 라임 세대 구분 (출처: Louis' blog, 2012)

| 세대 | 시기 | 특징 |
|---|---|---|
| 1세대 | 현진영(89)~김진표(98) | 무운 → 끝 한 글자만 맞추거나 동어 반복 |
| 2세대 | 98~2000 | 2~3음절 단어 반복 (대표: 주석) |
| 3세대 | 2001~ | 다음절 라임 시작. SNP(버벌진트·피타입·4WD·Defconn) |
| 4세대 | 2004~ | 모음조화 라임. 소울컴퍼니, 화나·칼날("최적화") |

**중요**: 2세대는 글자만 읽어도 공통점을 찾을 수 있으나, **3세대부터는 끊어 읽기·강세 변화 같은 '기술'이 더해지지 않으면 라임이 성립하지 않음** → 표기 기반 매칭과 발음 기반 매칭이 질적으로 다르다는 근거.

### 3.3 아티스트별 기법 (실측 검증 완료)

| 아티스트 | 기법 | 검증 방법 |
|---|---|---|
| 화나 | 동일 모음 구조 반복(고밀도). 본인이 "동일 모음 구조"를 의도적으로 짠다고 언급 | 실제 곡 발췌 분석, 같은 rhymeUnit 4회 반복 확인 |
| 피타입 | 초성 완전 무관, 종성은 조음 유사군으로 인정. "청각적 라임" 추구 | 실제 인용구 분해 — 초성이 전부 달라도 라임 성립 확인 |
| 래원 | 극단적 밀도, 개연성 포기 | 34음절 중 14음절(41%)이 단 2개 모음군에 집중 |
| 딥플로우 | 기교보다 리리시즘 안에서의 라임 배치 (저밀도 극단) | 정성적 자료만 |
| 블랙넛 | 동음이의어/이중의미 펀치라인 | **음운 매칭이 아님 → 본 엔진 범위 밖** |

### 3.4 선행 도구 레퍼런스

- **RhymeBot** (2019 한국정보과학회 발표, [github.com/duckduckhero/RhymeBot-Web](https://github.com/duckduckhero/RhymeBot-Web))
  - **KoG2P로 실제 발음 변환** 후 비교
  - 모음 5개 그룹 / 자음 5개 그룹으로 정규화
  - **변형 LCS**로 유사도 계산: `lcs_length(w1,w2) / max(len(w1), len(w2))`
- **g2pK** ([github.com/Kyubyong/g2pK](https://github.com/Kyubyong/g2pK)) — Mecab 기반 한국어 G2P, Python
- **Korhyme** — 발음 유사도 기반 라임 검색기 (도메인 만료, 접속 불가)
- **논문**: "딥러닝 기반 언어 모델들을 활용한 라임 기반 한국어 랩 가사 생성 시스템"(2021, KIISE)
  - **가사 생성기(Lyrics Generator) + 라임 필터(Rhyme Filter)** 2단 구조 — 본 설계의 생성 파이프라인과 동일 구조

## 4. 매칭 엔진 설계

### 4.1 핵심 원칙

1. **발음 기준** (표기 아님) — G2P 변환 후 비교
2. **초성 무관** — 피타입 사례로 실증됨
3. **자모 그룹 정규화** — 유사 조음군끼리 묶어서 부분점수 인정
4. **LCS 기반 유사도** — 끝에 고정하지 않고 최장 공통 패턴을 찾음

### 4.2 폐기된 접근 (실패 기록)

자체 설계했던 **위치 가중치 방식**(끝음절에 최고 가중치를 주고 앞으로 갈수록 감소)은
피타입의 실제 라임 사례에서 **정작 끝음절만 다르고 앞이 모두 맞는 경우를 낮게 평가**하는 버그가 확인되어 폐기.
LCS는 끝 고정이 없어 이 문제가 구조적으로 발생하지 않음.

### 4.3 두 개의 함수

| 함수 | 용도 | 입력 | 출력 |
|---|---|---|---|
| `endRhymeScore(a, b, n)` | 저장 항목 간 끝라임 비교 (검색/DB 매칭) | 두 텍스트 | 0~1 점수 |
| `internalDensity(text)` | 한 줄 자체의 라임 밀도 분석 (작사 보조/생성 검증) | 한 텍스트 | 밀도 + 클러스터 목록 |

둘 다 **G2P 변환된 음소열** 기준으로 재작성 필요. 현재 프로토타입은 표기 기준 1차 근사치.

### 4.4 밀도 지표에 대한 주의

- 밀도는 **"높을수록 좋다"가 아님**. 아티스트별·구간별로 의도적으로 다르게 가져가는 값.
- 벌스 안에서 어떻게 완급을 조절하는지에 대한 **정립된 외부 이론이 없음** → 자체 설계 필요 항목.
- 실측 확인: 받침 유무는 밀도 점수에 편향을 주지 않음 (동일 반복횟수·간격이면 동일 점수).

## 5. 데이터 구조

### 5.1 저장 원칙

**원문 가사 텍스트는 저장하지 않는다.** G2P로 변환한 **음운 데이터(음소 시퀀스)만** 저장.
→ "소리나는대로" 분류한다는 설계 원칙과, 저작권 리스크 회피가 동시에 달성됨.

### 5.2 스키마

**`LYRICS`** — 사용자가 직접 입력한 가사 조각 (단어/문장 구분 없음)

| 컬럼 | 설명 |
|---|---|
| id | PK |
| user_id | 작성자 |
| text | 사용자 본인이 작성한 원문 |
| syllable_count | 음절 수 |
| status | 사용/삭제 |

**`RHYME_INDEX`** — 음절 단위 분해 결과 (LYRICS 1:N)

| 컬럼 | 설명 |
|---|---|
| lyric_id | FK |
| position | 텍스트 내 음절 위치 (0부터) |
| jung | 중성 (G2P 변환 후) |
| jong | 종성 (G2P 변환 후, 없으면 '') |
| rhyme_unit | jung+jong — 라임 비교의 최소 단위 |

**외부 코퍼스 기반 라임 사전**은 `RHYME_INDEX`와 동일한 음운 데이터 형태로만 적재하고,
출처는 메타데이터(아티스트/곡명)로만 참조한다.

## 6. 스타일 슬라이더

### 축: 라임밀도 ↔ 의미전달

```
[의미 우선] ●──────────○──────────● [사운드/라임 우선]
   딥플로우          화나/피타입          래원
```

- 슬라이더 값 = `internalDensity()` 의 **목표 밀도 파라미터**로 직결
- 낮게 → 검증 통과 기준 완화 (의미 살리는 방향)
- 높게 → 반복·압운 강제 (사운드 우선 방향)

아티스트 프리셋으로도 선택 가능:

| 프리셋 | 설정 |
|---|---|
| 화나 | 동일 모음 반복 밀도 가중치 ↑ |
| 래원 | 극단적 밀도, 의미 제약 완화 |
| 피타입 | 종성 그룹 매칭 허용범위 넓게 |
| 딥플로우 | 밀도 낮게, 의미 우선 |

## 7. 기능별 파이프라인

### 7.1 라임 검색 (LLM 미개입)

```
사용자 입력 → G2P 변환 → rhyme_unit 시퀀스 생성
  → RHYME_INDEX 조회 (끝라임 / 내적라임 부분일치)
  → LCS 점수순 정렬 → 결과 반환
```

### 7.2 가사 생성 (LLM 개입)

```
① 사용자 입력: 주제/스토리 + 마디수(8·16, 확장 시 4·32) + 스타일 슬라이더
② ★LLM★ 음운 패턴을 재료로 새 문장 "조합" 생성
③ 엔진: G2P → 끝라임/밀도 채점 → 목표치와 비교
④ 미달 시 ★LLM★ 채점 결과를 피드백으로 받아 부분 재작성
⑤ ③~④ 반복 → 통과 시 최종 출력
⑥ (선택) 결과를 LYRICS에 저장 → 재활용
```

**역할 분담 원칙**
- **가사 작성 = LLM** (창작만 담당)
- **라임 찾기/검증 = 결정론적 도구** (판단 없이 계산만)
- LLM에게 "이게 라임이 맞는가" 판정은 **절대 맡기지 않는다** — 근거 없는 그럴듯한 답을 낼 위험

## 8. LLM 연동 계획

### 8.1 모델

| 용도 | 모델 | 가격(Input/Output, 1M) | 이유 |
|---|---|---|---|
| 초안 생성 (1회) | `claude-opus-5` | $5 / $25 | 자연스러운 조합에 창작 품질이 관건 |
| 부분 재작성 (반복) | `claude-haiku-4-5` | $1 / $5 | 반복 작업이라 속도·비용 우선 |

- 비용 절감이 우선이면 초안 생성도 `claude-sonnet-5`($2/$10)로 대체 가능
- `claude-haiku-4-5`는 `effort` 파라미터 미지원, thinking은 구식 `budget_tokens` 방식 → **코드 분기 필요**

### 8.2 연동

- SDK: `@anthropic-ai/sdk`
- 인증: `ANTHROPIC_API_KEY` 환경변수. **`.env` + `.gitignore` 필수** (기존 MySQL 비밀번호 노출 사고 반복 금지)
- 요청: `thinking: {type: "adaptive"}`, `output_config: {effort: "medium"}`, 스트리밍 권장
- 신규 라우트: `server/routes/generate.js`

### 8.3 G2P 서비스

`KoG2P` / `g2pK` 모두 Python + Mecab 의존 → Node.js 앱에 직접 탑재 불가.
**별도 마이크로서비스로 분리**하거나 JS 포팅 필요. (미결정)

## 10. 미확정 / 전제사항

1. **현재 프로토타입 수치는 전부 표기 기준 근사치.** G2P 적용 시 달라질 수 있음.
2. 자모 그룹 가중치(유사군 부분점수)는 실제 가사로 튜닝 필요.
3. 벌스 내 밀도 완급조절 방식 — 참고 이론 없음, 자체 설계 필요.
4. G2P 서비스 배포 형태 미결정 (마이크로서비스 vs JS 포팅).
5. 라임 사전 구축용 코퍼스 확보 경로 미정.
